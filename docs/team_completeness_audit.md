# 研发团队完整性审计（Team Completeness Audit）

对照一个完整的软件研发团队（从需求到生产运维的全生命周期），逐环节核对当前 AI-Team 运行时的现状。
现状基于仓库代码逐项核实（全量回归 2244 passed 基线，静态门禁 E9/F63/F7/F82 通过）。

## 一、生命周期覆盖总览

```text
需求 → 分析/澄清 ✅ → 版本规划 ✅ → 架构/UI-UX 设计 ✅ → 实现 ✅ → 测试/评审 ✅
→ 集成回归 ✅ → QA 对抗测试 ✅ → 安全审计 ✅ → 文档 ✅ → 验收 ✅
→ 发布门禁 ✅ → 发布（版本/说明/git 锚点）✅ → 监控契约 ⚠️（离线自检）
→ 部署就绪审查 ✅ → 清单/打包 ✅ → 缺陷回流/热修 ✅
```

## 二、角色配置核对

| 角色 | 状态 | 说明 |
|------|------|------|
| 需求分析师（analyst） | ✅ | 任意明确程度需求 → REQ 编号/优先级/验收标准/【假设】/【待确认问题】 |
| 规划（planner） | ✅ | 需求拆解与任务图 |
| 架构师（architect） | ✅ | 结构与接口设计 |
| UI/UX 设计师（ui_ux） | ✅ | 仅对需要界面的项目启用（T12） |
| 开发（developer 池 + 专项技能） | ✅ | 多实例并行、依赖调度、前端/后端/数据等专项提示词（T12） |
| 测试（tester） | ✅ | 测试证据审查（TEST_PASSED / TEST_FAILED） |
| 评审（reviewer） | ✅ | 代码质量门禁（APPROVED / REVISION_REQUIRED） |
| QA（qa） | ✅ | 产品级对抗测试，`QA_FAILED` 阻断发布（T6） |
| 安全工程师（security） | ✅ | 确定性安全审计复核，`SEC_FAILED` 阻断发布且不可被豁免（T15） |
| 发布/运维工程师（sre） | ✅ | 部署就绪审查，`SRE_READY` / `SRE_DEGRADED`（T16） |

| 文档工程师（doc_writer） | ✅ | 标准交付文档集 + 校验清单 |

三个治理角色（security / sre / release_manager）均为**零工具面**，其结论不修改任何产品文件、不执行命令。

## 四、标准软件开发流程对齐

| 标准 SDLC 环节 | 运行时对应阶段 | 门禁/证据 |
|------|------|------|
| 需求分析 | Analyst（分析前置于规划） | 结构化规格 + 待确认问题 |
| 设计 | Architect + UI/UX | 设计文档、设计规范入文档上下文 |
| 实现 | Developer 池 + Tester/Reviewer | 测试证据、评审结论 |
| 集成/系统测试 | 产品级集成回归（有界返工） | 回归证据，红色套件不打包 |
| 质量保证 | QA 对抗测试 | `QA_FAILED` 阻断发布 |
| 安全审查 | 确定性安全审计 + 安全工程师 | `SEC_FAILED` 阻断发布，不可豁免 |
| 文档 | DocWriter + 验收追溯矩阵 | 文档集 + 校验清单 |
| 验收 | 确定性追溯矩阵 | `PASSED` / `FAILED` |
| 发布审批 | 发布门禁 + 发布经理 | 确定性阻断项 + GO/NO-GO |
| 发布 | 版本/说明/git 锚点/发布日志 | `RELEASE_NOTES.md` + `release_log.json` |
| 部署与运维准备 | 监控契约 + SRE 就绪审查 | `MONITORING.md` + `docs/sre_readiness.md` |
| 交付归档 | 清单 + 打包 + 冒烟 | sha256 清单 |
| 缺陷处理 | 缺陷清单 → 热修 → 重新打包 | `docs/defect_report.md` |

## 五、结论与剩余边界

研发团队角色配置已齐全（12 类角色），标准 SDLC 的“需求→设计→实现→测试/QA→安全→文档→验收→发布门禁→发布→监控→部署就绪→归档→缺陷回流”在运行时均有对应阶段与确定性证据，质量门禁不再只依赖 LLM 判断。

仍存空白，均如实记录、未以模拟方式伪造：

1. 测试覆盖率阈值与性能基准（产品侧）。
2. 联机依赖漏洞库查询（离线环境记为 unavailable）。
3. API 参考文档自动生成。
4. 真实云部署/APM/告警接入与回滚执行——依赖客户目标环境，属于交付后的环境侧接入。
5. 数据迁移脚本规范。
