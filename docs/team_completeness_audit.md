# 研发团队完整性审计（Team Completeness Audit）

对照一个完整的软件研发团队（从需求到生产运维的全生命周期），逐环节核对当前 AI-Team 运行时的现状。
现状基于仓库代码逐项核实（全量回归 2052 passed 基线）。

## 一、生命周期覆盖总览

```text
需求 → 分析/澄清 ✅ → 产品规划 ⚠️ → 架构设计 ✅ → 实现 ✅ → 测试/QA ⚠️
→ 文档 ✅ → 交付打包 ✅ → 部署 ⚠️ → 运维/维护 ❌ → 反馈回流 ❌
```

## 二、逐环节审计

### 1. 需求与产品阶段

| 能力 | 状态 | 说明 |
|------|------|------|
| 需求结构化（任意明确程度） | ✅ | Analyst：REQ 编号/优先级/验收标准/【假设】/【待确认问题】 |
| 澄清工作流 | ✅ | --analyze-only → 客户答复 → --clarifications；交互式会话（--interactive/--resume-session） |
| 需求变更管理 | ❌ | 交付后客户改需求 → 缺少"变更→影响分析→增量任务图"回流（现有 recovery_replan 仅服务运行时失败重规划，不复用为需求变更入口） |
| 版本规划/优先级排序 | ❌ | 无 Release/迭代概念：多需求场景下没有里程碑、版本号（semver）与发布计划角色 |

### 2. 设计阶段

| 能力 | 状态 | 说明 |
|------|------|------|
| 架构设计 | ✅ | Architect（含守卫/验收门禁） |
| UI/UX 设计 | ❌ | 无设计角色：GUI/Web/有界面的项目缺少布局、交互与可用性设计环节（当前仅适合纯 CLI/库类交付） |
| 数据模型/迁移设计 | ⚠️ | Architect 可描述 schema，但无迁移脚本规范（如 alembic 类约定），交付后演进数据库无章可循 |

### 3. 实现阶段

| 能力 | 状态 | 说明 |
|------|------|------|
| 多 Developer 并行实现 | ✅ | Developer 池 + 依赖调度 + 资源治理 |
| 工具沙箱/权限/审计 | ✅ | Job Object 进程沙箱 + 能力策略 + 执行历史 |
| 确定性静态质量门禁 | ❌ | ruff/mypy 已在工具白名单，但没有强制 lint/type 门禁阶段；代码质量仅靠 Reviewer（LLM 判断） |
| 测试覆盖率门禁 | ❌ | 无 coverage 统计与阈值（tester 只审"证据存在与通过"） |
| 专项开发角色 | ❌ | Developer 是通用角色：前端/后端/数据工程师无区分，复杂全栈项目缺少技能匹配 |

### 4. 测试与 QA 阶段

| 能力 | 状态 | 说明 |
|------|------|------|
| 测试证据审查 | ✅ | Tester（TEST_PASSED/FAILED + 最新证据规则） |
| 验收测试 | ✅ | 确定性 REQ 追溯矩阵（--strict-acceptance 可阻断） |
| 探索性/对抗测试 | ❌ | 无独立 QA 角色：测试由 Developer 自己写自己跑，缺少"试图打破产品"的对抗用例（边界/异常输入/并发） |
| 性能测试 | ❌ | 交付物无性能基准与阈值验证（运行时自身有 benchmark，产品没有） |
| 依赖漏洞扫描 | ❌ | dependency_policy 只管版本钉死；无 pip-audit 类漏洞检测 |

### 5. 文档阶段

| 能力 | 状态 | 说明 |
|------|------|------|
| 五份标准文档 + 验收报告 | ✅ | DocWriter + 确定性追溯矩阵 |
| 交付清单 | ✅ | DELIVERY_MANIFEST.md（sha256） |
| API 参考文档自动生成 | ❌ | 无 docstring→API 文档的生成环节 |

### 6. 交付与部署阶段

| 能力 | 状态 | 说明 |
|------|------|------|
| 交付包 + 引导安装器 + Dockerfile 模板 + 冒烟 | ✅ | packaging/deployment + 冒烟实测 |
| 交付物版本控制 | ❌ | HostGitOperationService 已实现但交付阶段未使用——交付物不入 git，无 tag/版本锚点 |
| 容器镜像实际构建 | ❌ | 仅 Dockerfile 模板；镜像构建依赖客户环境（已文档化） |
| 回滚执行 | ⚠️ | 部署文档提及回退，但安装器未实现"上一版本恢复" |

### 7. 运维与维护阶段（最大空白）

| 能力 | 状态 | 说明 |
|------|------|------|
| 交付后监控 | ❌ | 运行时自身有指标/告警/仪表盘，但**交付出的产品**没有接入任何监控 |
| 缺陷跟踪回流 | ❌ | 客户报告的缺陷无法回流为新任务（无 issue 概念与状态） |
| 修复→重新交付 | ⚠️ | runtime 支持断点续跑，但缺"缺陷→热修任务→重新打包"的标准化流程 |

### 8. 项目管理与横向能力

| 能力 | 状态 | 说明 |
|------|------|------|
| 多项目调度/资源隔离 | ✅ | multi_project_scheduler + 模型治理（预算/熔断/回退） |
| 成本核算 | ⚠️ | 模型用量/成本内部有台账（ModelUsageLedger/ProjectCostProjection），但 CLI 结果与交付文档**不输出**成本报告 |
| 跨项目知识库 | ❌ | 无经验沉淀：历史交付的模式、踩过的坑、组织规范不会影响后续项目 |
| 事件/审计/仪表盘 | ✅ | 全链路事件溯源 + 仪表盘导出 |

## 三、缺失角色清单（按价值排序）

| 角色 | 对应空白 | 优先级 |
|------|----------|--------|
| QA/探索性测试工程师 | 对抗性测试、边界与异常输入、超出 Developer 自测范围的破坏性尝试 | 高 |
| 安全工程师 | 交付物安全扫描（secrets 泄漏/注入面/依赖漏洞）与安全审查证据 | 高 |
| 发布/运维工程师（SRE） | 交付物版本控制（git/tag）、监控接入、回滚执行 | 高 |
| 产品经理（Release 管理） | 多需求优先级、版本规划、需求变更受理 | 中 |
| UI/UX 设计师 | 有界面项目的布局/交互/可用性设计 | 中（视项目类型） |
| 前端/后端/数据专项开发 | Developer 技能匹配与专用提示词 | 中 |
| 技术文档细化（API 参考） | docstring → API 文档生成 | 低 |

## 四、建议实施顺序（下次立项参考）

1. **确定性静态门禁**（ruff + mypy + pip-audit 作为证据门禁阶段）——低成本高确定性，直接补齐"代码质量不只靠 LLM 判断"
2. **交付物 git 版本控制**（复用 HostGitOperationService：init/add/commit/tag）——交付可追溯、可回滚
3. **QA 对抗测试角色**——独立于 Developer 的破坏性验证，补齐测试独立性
4. **成本报告**——把已有台账暴露到交付结果与文档
5. **需求变更回流**——变更文件 → Analyst 受理 → 增量任务图（复用 replan 机制）
6. **UI/UX 与专项开发角色**——按项目类型启用
7. **交付后监控/缺陷回流**——需要部署目标环境配合，最后做

## 五、结论

当前运行时在**单次交付闭环**（需求→产品→文档→打包→验收）上已完整且经实弹验证；
主要空白集中在**交付之后**（运维、缺陷回流、版本演进）与**质量独立性**（静态门禁、
对抗 QA、安全扫描），以及**组织记忆**（知识库、需求变更管理）。按上表顺序补齐即可
逐步逼近完整研发团队的能力边界。
