# Executable Acceptance Evidence

## Purpose

The existing requirement traceability report checks whether REQ-xxx identifiers appear in documentation. That is useful document traceability, but it does not prove that an acceptance test ran. The executable evidence engine adds that missing link:

`REQ → AT test ID → JUnit selector → actual integration-run case → outcome/report`

The deterministic evaluator does not infer a pass from an Agent statement or from a requirement identifier appearing in `test_report.md`.

## Acceptance test manifest

Place `acceptance_tests.json` under the deliverable's `docs/` directory:

```json
{
  "schema_version": 1,
  "tests": [
    {
      "test_id": "AT-001",
      "requirement_id": "REQ-001",
      "selector": "tests.test_word_count::test_counts_words"
    }
  ]
}
```

Rules:

- `test_id` is a stable project acceptance-test identifier beginning with `AT-`.
- `requirement_id` must match an identifier parsed from the analyst's requirement specification.
- `selector` is the exact JUnit selector `<classname>::<testcase name>`, not a shell command.
- One mandatory requirement must map to at least one acceptance test.
- Every mapped selector must appear in the JUnit report generated by the product integration run and must pass. A missing selector, skipped case, failed case, or invalid manifest cannot pass acceptance.
- A test may cover more than one requirement. Multiple tests may be mapped to one requirement; all mapped tests must pass.
- Optional requirements without executable tests produce warnings, not mandatory release blockers.

The integration runner executes the deliverable test suite in a fresh staging copy and writes a JUnit XML report. DocWriter can propose the manifest from the requirement list and the observed JUnit selectors, but the host validates every requirement ID and selector against those observed values before writing it. Existing project-authored manifests are preserved. The evidence evaluator consumes the test cases from that report; it does not run arbitrary commands from the manifest. The actual runner command, exit code, suite summary, test selector, status and duration are retained in the evidence report.

## Freshness and release behavior

Evidence is considered stale after 24 hours. The report records the evidence start time and age. The following states are distinct:

| State | Meaning | Release |
| --- | --- | --- |
| `passed` | Every mandatory REQ has mapped, executed, passing tests and fresh evidence | Eligible for other gates |
| `failed` | Missing mapping, failed test, failed suite, invalid manifest, or orphan REQ mapping | Blocked |
| `not_executed` | Suite skipped or one or more mapped mandatory selectors did not execute | Blocked |
| `stale` | Execution timestamp is missing, invalid, or older than 24 hours | Blocked |
| `not_applicable` | No parsed requirements exist | No acceptance blocker |

The project release gate consumes this verdict. A Release Manager Agent cannot override a deterministic acceptance blocker.

## Manual UAT

Human UAT is intentionally not inferred from generated markdown or Agent messages. A future signed UAT provider may add externally verifiable approval evidence; until then, manual sign-off remains an external process and is not counted as executable test evidence.

## Reports

- `docs/acceptance_report.md`: document-level requirement traceability.
- `docs/executable_acceptance_report.md`: executable selectors, actual run outcomes, command and summary, evidence age, gaps and warnings.
